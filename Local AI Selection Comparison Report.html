01先算清 8G 显存到底剩多少

很多"模型跑不动"的问题，其实是账没算对。显存不是 8G 全给模型用。

占用项 典型值 说明
Windows 桌面合成 + 浏览器0.6 - 1.2 GB12490F 无核显，桌面渲染也吃这块显存。开着浏览器会更吃。
CUDA 上下文 / 运行时0.3 - 0.5 GB驱动层固定开销，无法避免。
实际可用给模型6.3 - 7.1 GB这才是真正的预算。所有选型都要卡在这个数里。

直观一点：

8 GB 物理显存可用 6.3-7.1 GB
模型 + KV cache 可用区系统与桌面占用约 18%

32G 内存的作用是接住"溢出"的部分。量化后体积超过 6.5 GB 的模型，多出来的层会被塞进内存，速度按溢出比例下降：

溢出量 速度损失 体感
0（全驻留）无正常，够快
1 - 2 GB约 50-60%能用，但明显变慢
3 - 6 GB约 80-90%基本只能挂着等
10 GB 以上95%+不可用，等于 CPU 推理
一条硬规则：模型文件 ≤ 6.0 GB 是 8G 显存的"舒适线"。超过就要开始付速度税，而且这个税不是线性的——溢出 1 GB 就砍一半速度。

五款候选，按"在你的硬件上实际能跑成什么样"排序，不是按参数大小排。

溢出 10 GB		 2-4 t/s 不可行，列出来是为了让你死心。智能确实顶尖，但 2-4 tok/s 意味着写 500 字要等 4 分钟以上。32G 内存扛得住，人的耐心扛不住。

为什么第 1 名和第 2 名差距这么大

14B 只比 8B 多 6 个 B 的参数，但量化后从 5 GB 涨到 9 GB，刚好跨过 6.3-7.1 GB 这条线。跨线的代价不是"慢一点"，而是"三分之一的计算单元要去内存里搬数据"——GPU 到内存的带宽只有显存的十几分之一，这就是速度掉 4 倍的原因。

所以 8G 显存上，8B 是性价比的顶点，不是妥协。想要更高智能，只能换硬件，没有中间路线。

Gemma 的许可证要单独说：Gemma 使用条款包含一份"禁止使用政策"，明确限制若干用途，Google 保留终止授权的权利。你要的是"基本无审查"，一个在法律文本上就有用途限制的底座，技术上再消融也没解决合规层面的问题。Qwen3 是 Apache 2.0，Llama 3.1 是社区许可（有 7 亿月活限制但个人使用不受影响），这两个更干净。

关于 Flux 的更正：我前面说"8G 跑 Flux 基本不现实"是不准确的。2026 年的 GGUF 量化方案（Q4_K_M 约 7 GB）配合 ComfyUI 的 offload，8G 显存确实能跑，Flux Schnell 4 步版甚至不慢。但它不适合你——不是跑不动，是 Flux 的 NSFW 需要额外 LoRA 硬撬，而 SDXL 系模型天生就会画。选型要看目标，不是看参数。

SDXL 系在 8G 上的实际能力边界

能做的：

  • 1024×1024 或 832×1216 原生分辨率出图（需 --lowvram）
  • 同时叠加 2-3 个 LoRA
  • 1 个 ControlNet（两个要非常小心）
  • 中分辨率的 face detailer 和局部重绘（inpaint）

做不了的：

  • 4K 原生生成（只能靠后期放大）
  • 3 个以上 ControlNet 同时启用
  • 批量出图（batch 只能设 1）
  • LoRA 训练（至少要 12G 显存）

04图片生成的依赖拆解

"装个模型就能出图"是错觉。一个能跑的工作流至少依赖六个组件，缺一个就出不了图。

组件 必需性 体积 作用与缺失后果
Checkpoint
models/checkpoints/		 必需 6.5-7 GB 主模型，决定画风和能力上限。缺了什么都干不了。
VAE
models/vae/		 SDXL 建议 335 MB 负责潜空间↔像素转换。SDXL 部分模型自带的 VAE 有问题，不换会导致出图发灰、对比度低、细节糊。这是新手最常踩的坑。
CLIP 文本编码器
内置在 checkpoint		 必需 — SDXL 需要 clip_l + clip_g 双编码器，已打包在 checkpoint 里，不用单独下。ComfyUI 会自动加载。
采样器
内置		 必需 — ComfyUI 自带 euler_ancestral、dpmpp_2m_sde 等。SDXL 推荐 dpmpp_2m_sde + karras，25-30 步。
LoRA
models/loras/		 可选 50-300 MB/个 控制具体角色、服装、画风。这是本地生成相比在线服务最大的优势所在。建议挑 3-5 个，别囤。
放大模型
models/upscale_models/		 可选 60-70 MB 4x-UltraSharp 或 ESRGAN。8G 显存出不了 4K，靠它后期放大。
ControlNet
models/controlnet/		 可选 2.5 GB/个 用姿态、线稿、深度图约束构图。对"想要特定姿势"的场景很有用，但每个 2.5 GB，8G 上只能挂一个。

8G 跑 SDXL 时，显存是怎么被吃掉的

阶段显存占用说明
加载 checkpoint（fp16）6.6 GB全量加载，此时已接近上限
文本编码（CLIP 双塔）+1.6 GB编码完可以释放
扩散迭代（1024²）+1.8 GB潜空间 + 中间激活值
VAE 解码+1.0 GB最后一步，把潜空间还原成图
理论峰值11 GB超过 8G，所以默认必崩

ComfyUI 的 --lowvram 做的就是：把 checkpoint 拆成子模块，只把当前正在算的那一块放进显存，算完就换出去。代价是每次切换有 PCIe 传输开销，所以速度降 30-50%，但峰值被压到 7.2 GB 左右——刚好卡进可用区间。

实时预览会额外吃显存。ComfyUI 的 Preview 节点、或者开着浏览器实时看进度，都会多占 200-400 MB。8G 上如果反复 OOM，先把预览关掉，往往就好了。

05文字和图片抢显存的问题

你的场景是"一个人用"，但一个人也可能想边聊边画。8G 上这件事做不到。

组合 总需求 结果
Ollama 8B 常驻 + ComfyUI 出图6.2 + 7.2 = 13.4 GB必崩，ComfyUI 侧 OOM
Ollama 卸载后 + ComfyUI 出图7.2 GB正常
Ollama 8B + SD1.5 出图6.2 + 3.2 = 9.4 GB仍会崩，SD1.5 也救不了

所以只能串行。三个办法让切换不那么难受：

  • 设 OLLAMA_KEEP_ALIVE=0：每次回答完立刻释放显存，代价是下次提问重新加载模型（多等 3-5 秒）。这是最省心的方案。
  • 手动 ollama stop qwen3-8b：切换前敲一条命令，显存立刻清空。
  • 用完 ComfyUI 不清缓存：ComfyUI 默认常驻模型在显存里（切图快），但如果接下来要用文字模型，得在界面里点 "Free model and node cache"。

判断当前有没有被占：任务管理器 → 性能 → GPU → 看「专用 GPU 内存」。空闲应该低于 0.8 GB，被占会显示 5-7 GB。

06联网安装的最短路径

不用做离线准备，直接装。整个流程约 40 分钟，其中 30 分钟在等下载。

联网最大的好处是「可试错」。模型选错了重拉一次，节点装坏了删掉重装，版本冲突了回滚——都是几分钟的事。所以别在选型上纠结太久，装上跑两天，手感比参数表准。

  1. 装 Ollama，先把模型目录挪到 E 盘

    默认会存 C:\Users\你的用户名\.ollama\models，一个 14B 就 9 GB，C 盘本就紧张。装完立刻加系统环境变量：

    OLLAMA_MODELS = E:\ollama\models

    设完从托盘退出 Ollama 再启动，让变量生效。

  2. 拉第一个模型，别贪多

    ollama run huihui_ai/qwen3-abliterated:8b

    先只拉这一个。跑两天，觉得速度够、质量不够，再 ollama pull :14b；觉得慢就换 :4b。一次只拉一个，不然下了 20 GB 才发现方向不对，纯浪费。

  3. 解压 ComfyUI，放模型，加启动参数

    解压到 E:\ComfyUI（路径不能有中文和空格），模型按目录归位：

    models\checkpoints\      ← NoobAI-XL / Illustrious / SD1.5
models\vae\              ← sdxl_vae.safetensors
models\loras\            ← 角色/风格 LoRA
models\upscale_models\   ← 4x-UltraSharp.pth

    然后编辑 run_nvidia_gpu.bat，末尾加 --lowvram：

    .\python_embeded\python.exe -s ComfyUI\main.py --windows-standalone-build --lowvram

    便携版自带 Python 和 PyTorch，不碰系统环境，装坏了直接删文件夹重来。

  4. 需要扩展就装 ComfyUI-Manager

    节点从它里面搜着装，依赖会自动 pip install。联网状态下这一步很顺，但要知道风险：custom node 本质是 Python 代码，装了就有执行权限。只从 Manager 里下载量高的装，别碰来路不明的节点包。

  5. 跑通验收

    • 文字：能连续对话 10 轮不崩，8K 上下文下速度不塌
    • 图片：SDXL 能出 1024 图，SD1.5 也能出（验证 VAE 路径正确）
    • 显存：出图时任务管理器显示专用 GPU 内存 7 GB 左右，不爆
    • 切换：ollama stop 之后显存能回到 0.8 GB 以下
联网状态才需要注意的三件事：
1. 模型会被下架。HuggingFace 和 Civitai 上这类仓库随时可能被隐藏或删号。看到能用的就下到本地存着，别只收藏链接。
2. Ollama 的 tag 会漂移。:8b 背后指向的具体版本可能被作者更新。如果某个版本特别顺手，用 ollama show --modelfile 记下 digest，日后能还原。
3. 本地推理确实不联网。Ollama 和 ComfyUI 的推理全程在本机，不传数据。但别用那些"在线版 WebUI"或云 API 代理，那是另一回事。

07取舍与限制

这部分不好听，但比推荐列表重要。

一、8G 显存的天花板是硬的

所有"优化技巧"（量化、offload、lowvram）本质都是用速度换空间，不能凭空变出算力。你在这套硬件上能做到的最好状态就是：8B 文字模型全速 + SDXL 1024 出图 50 秒一张。想要 14B 全速或 4K 直出，只有换卡一条路。

如果哪天想升级，显存优先级远高于核心性能。一张 3060 12G 在出图上比 4060 8G 更好用，因为 12G 能全量加载 SDXL 不用 offload。

二、小模型的 NSFW 质量有天然缺陷

这不是审查问题，是能力问题。8B 参数和 SDXL 底座在人体结构、手部、多人场景上的表现就是不如更大的模型，而 NSFW 恰好是这些细节最密集的场景。常见崩坏：手指数量错误、肢体连接断裂、多人时肢体混淆。

缓解手段：用负向提示词压（bad hands, extra digits, missing fingers）、降分辨率到 832×1216、接 face detailer 做局部重绘、出图后手动挑。指望"一次成型"会失望。

三、去审查不等于没有边界，也不等于没有责任

技术层面：abliterated 模型确实能做到 0/100 拒答，这是事实。但它只是"不再拒绝回答"，不代表"答得对"——模型在陌生领域会硬着头皮编，这比拒绝更有欺骗性。用久了你会发现，它偶尔的"胡编"比偶尔的"拒绝"更难察觉。

「不传播」是对的那条线，而且是最关键的一条。法律上"传播"和"制作自用"的定性差别很大：前者落入刑法范畴，后者主要是治安管理层面。守住不传播、不上传、不分享，风险量级完全不同。

但也别把"不传播"理解成"完全无风险"。制作行为本身在《治安管理处罚法》里有对应条款，执法实践中对"仅自用"的处理各地不一，不是一句"我没传"就能免责。涉未成年人的内容没有任何解释空间，这一点不论传播与否、不论是否本地、不论是否虚构，都不要碰。真要弄清楚自己的边界，找律师问，别信网上任何一方的说法——包括我这段。

四、联网意味着模型会"悄悄变化"

离线部署有个隐性好处：文件一旦落盘就不再变。联网之后，ollama pull 拿到的可能是作者更新过的版本，某个 LoRA 可能被替换，某个节点可能升级后行为不一致。哪天你发现"同一个提示词效果不如上周"，不一定是你的问题。

做法很简单：用得顺手的版本记下 digest，模型文件拷一份到备份盘。这类仓库被下架、被改、被删是常态，本地存一份才真正属于你。硬盘比链接可靠。
